# 개발 계획과 검증 기준

이 문서의 구현 순서는 모두 **제안**이다. 첫 교육이 용해라는 기획만 확정되어 있다. 일정·인력·비용은 추정하지 않는다.

## 0. 기반 결정

대상 플랫폼·입력·엔진을 고르고 기존 코드가 있는지 확인한다. 성공 기준은 실행 가능한 빈 프로젝트와 선택 근거 기록이다. 현재 예정 개발 경로는 `C:\개인플젝\대장장이`다. 경로 지정은 엔진이나 버전 관리 선택을 의미하지 않는다.

## 1. 용해 한 건 완주

작업 배정 → 단순 용해 조작 → 공정 평가 → 급여 → 기록 저장을 연결한다. 임시 수치는 제안으로 표시한다. 완료 기준은 새로 시작·정상 완료·중단·결과 재열기·저장 재로드에서 결과와 잔액이 일관된 것이다.

## 2. 단조 형태 실험

3D 데이터와 하나의 단순 표시 방식을 구현한다. 단일 타격의 형태 변형과 목표 비교를 확인한다. 화면상 모양은 같아도 내부 두께가 다른 샘플을 구분하고, 저장 후 복원할 수 있어야 한다. 성능 측정 기준은 대상 장치 결정 후 정한다.

## 3. 단순 공정 연결

주조·조립·연마를 짧은 상호작용으로 추가한다. 후속 공정의 재료 상태와 평가 책임을 분리한다. 미참여 공정 결과를 변경해도 플레이어의 평가가 달라지지 않아야 한다.

## 4. 튜토리얼 완주

공정 개방 순서와 입단 조건을 결정한 뒤 모집부터 정식 입단까지 연결한다. 기록부와 의뢰 마무리 상태를 저장한다. 낮은 평가의 처리와 중간 종료 후 복구도 확인한다.

## 5. 플레이 검토

사용자가 평가 이유를 이해하는지, 품질별 급여 차이가 ‘약간’으로 느껴지는지, 단조가 핵심 공정으로 느껴지는지 확인한다. 확인 결과를 결정 기록에 남긴다. 정식 입단 이후 콘텐츠는 별도 기획 범위로 다룬다.

## 우선 확인할 위험

- 형태 모델 선택이 목표 장비를 충분히 표현하지 못할 수 있다.
- 내부 3D 상태를 화면에서 이해하기 어려울 수 있다.
- 서로 다른 공정 점수의 단순 평균은 반복 공정 편향을 만들 수 있다.
- 저장·정산 경계가 분리되면 중복 지급이나 누락이 생길 수 있다.
- 단순 공정을 늘리다 단조의 비중이 약해질 수 있다.
